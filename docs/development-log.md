## 2026-11-06：订单结算阶段、完成后售后与状态统一推导（当前工作区，未提交）

- 按用户确认的方案，将支付后起算改为“支付成功 → 待结算 → 实际结算完成”，发货后起算为“支付成功 → 待发货 → 首次有效物流起算/已发货 → 实际结算完成”；数据库模式值不变。结算余额划转、结算记录与正常订单完成在同一事务落地；0 天可以同次完成。保证金释放独立，部分退款主状态不被结算覆盖。
- 新增 `OrderLifecycleService` 统一推导主状态；已完成不阻止争议、退款或拒付。人工审核放宽合理来源，关闭后按结算/物流/售后事实恢复，活动审核及未结清反向资金独立阻止结算/释放。保留原周期、账务快照、唯一流水、部分退款后拒付人工核对及商户优先锁序；移除人工直接标记完成。
- 新增网关状态、时间、本地版本及正常阶段字段，以及 `order_gateway_status_events` 接收审计；只保存标准化白名单摘要。网关回调与主动查询保留当前尝试引用及重复/乱序保护，查询 `paid` 不再抹掉已结算、售后或人工审核事实。[D-29](decisions.md#d-29-订单主状态由结算与售后事实统一推导) 记录对 D-18 的替代关系。
- 后台拆分主状态/真实结算/物流及反向记账筛选，完成后可补录物流但不倒退；导入、未发货提醒、观察者、状态颜色和中英文文案同步。API 创建/查询/上传物流保留旧 `status` 的待结算→`paid` 映射，新增 `order_status/settlement_status/shipping_status`；首次支付通知固定 `paid`，付款提醒、广告转化不因完成或恢复重复触发。[架构](architecture.md)、[数据库](database.md)、[API 手册](../doc/api.md) 与在线中英文接口说明同步。
- 可靠性补充：首次商户通知和广告转化尝试与支付事实同事务保存，提交后派发，避免通知创建失败但支付状态已提交导致重试漏通知；历史待支付订单本次首次确认收款可经可靠待办补偿原即时入账，不补造既有历史收入。本地已标反向但无网关新字段/待办的旧单同样按本金证据阻止保证金释放。
