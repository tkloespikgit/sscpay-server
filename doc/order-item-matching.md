# 订单商品匹配逻辑（OrderItemService）

`app/Services/OrderItemService.php`：当下单未传商品明细时，从选定支付方式绑定的
站点商品变体（`site_product_variations`）中自动匹配出一份商品明细，凑出目标金额。

匹配对象始终是**变体**（每个变体有独立 SKU / 价格），父商品只提供名称和详情页链接。
变体价格统一以 **USD** 存储，所有匹配计算都在美金口径下进行，最后再按汇率折算成
订单交易币种。

支持两种模式：

- **RANDOM 模式**（`matchItems`）：给定一个目标金额，随机凑出一批商品，凑不满时改价补齐。
- **CREATE 模式**（`createItems`）：给定商户已传的商品明细，逐条找同价商品，找不到就复制改价、在站点上新建商品。

---

## 一、RANDOM 模式：`matchItems()`

输入：支付方式、目标商品金额（订单币种）、汇率。
先把目标金额折算成美金 `targetUsd`，再调用核心贪心算法 `fillByGreedy()` 凑单，
最后把结果折算回订单币种。

### 1. 候选池

取该支付方式下所有 `price > 0` 的变体，**打乱顺序**后作为候选池（避免同价变体
总是命中同一个）。

### 2. 贪心主循环（每轮选 1 个商品）

```
while 剩余额度 > 0:
    候选 = 剩余额度买得起 且 未达该变体件数上限 的变体
    候选 = 候选中单价最高的 10 个（RANDOM_POOL_SIZE）
    若候选为空：改用"件数上限放宽到临界值"再选一次
    若仍为空：跳出循环，进入"末件改价补齐"
    从候选 10 个中随机选 1 个
    数量 = min(剩余额度能买的最多件数, 该变体本轮件数上限)
    剩余额度 -= 单价 × 数量
```

要点：
- 每轮只挑**买得起的、单价最高**的一批，再随机选，是为了**尽快、尽量用少的行数**
  逼近目标金额，同时保留随机性避免商品组合千篇一律。
- 单个变体的件数上限**每次匹配随机确定**（`order_match.max_item_quantity` 只是
  随机上限的临界值，默认 3，配成 0 表示不限制），随机值在 `1 ~ 临界值` 之间，
  让同一单里各商品的件数分布不完全一样。随机上限内挑不出下一件时才放宽到临界值兜底。

### 3. 末件改价补齐

当剩余额度连候选池里最便宜的变体都买不起时（比如剩 $0.8，最便宜的商品要 $5），
不再新增整件商品，而是**改价补齐最后一件**，让匹配小计与目标金额分毫不差：

1. 优先挑"**原价不低于剩余额度、且最接近**"的变体，小幅打折凑到剩余额度
   （只打折、永不涨价）。
2. 若这次改价的折扣深度低于阈值（`order_match.min_price_ratio`，默认 0.4，
   即改价不能低于原价的 40%），说明"降太多"，则**回溯**：把上一行已选的商品
   退回一件，把预算还给剩余额度，额度变大后再重新挑一次改价商品。
   - 最多回溯 `MAX_BACKTRACK_ROUNDS`（3）轮。
   - 若回溯后的额度已经超过候选池里最贵变体的原价（再挑只能涨价），停止回溯，
     直接接受当前折扣较深的结果。
   - 若没有行可退（比如小额订单，第一件都买不起），直接进入兜底。
3. **深折扣兜底**：所有变体原价都低于剩余额度、或已无行可退时，从最便宜的
   10 个变体里随机选 1 个，直接改价到剩余额度（不再看折扣阈值）。

改价行在最终返回结果里，商品名会附加折扣百分比文案，例如
`XXX Card ($16) (60% discount)`，避免"原价 16 美金卖 0.6 美金"的观感异常。

### 4. 商品池容量校验

若件数上限是有限值（非 0），会先算一遍"候选池所有变体 × 临界值件数"的总容量，
不够打满目标金额直接抛异常，避免硬凑出改价离谱的结果。

### 5. 返回结构

```
{
  items: [{ product_sku, product_id, product_url, product_name,
            unit_price, quantity, total_price, converted_unit_price }, ...],
  subtotal: "...",   // 匹配小计（订单币种），恒等于目标金额
  overflow: "0",      // 保留字段，末件改价补齐后恒为 0
}
```

## 二、CREATE 模式：`createItems()`

用于商户下单时**已经传了商品明细**（`order_items`，每行自带下单时快照的 USD
折算单价）的场景，需要在站点侧"复现"出对应的真实商品（因为 `/pay` 远程建单
需要传真实的商品 ID / 链接），所以**必须同步完成，不走队列**。

逐条处理每个 `order_item`：

### 1. 同价匹配（优先）

在候选变体里找 USD 单价与目标价 `targetUsd` 相对误差 ≤ 5%
（`CREATE_PRICE_TOLERANCE`）且最接近的一个（候选先打乱再排序，价差相同时随机命中）。
命中就直接用它，不新建商品。

### 2. 找不到同价：复制改价新建

1. 取候选里**价格更高、且最接近**目标价的变体作为"模板"；如果连更贵的都没有，
   直接抛异常（没法只靠改价把便宜商品变贵）。
2. 调用站点 WooCommerce REST API（`/wc/v3/products`），以模板所属父商品的
   描述/图片/分类为基础，**复制一个新商品**：
   - 名称沿用源商品真实名称（为空则用"虚拟商品前缀 + 随机串"）；
   - 无论模板是不是变体商品，复制体一律建成**简单商品**（`type: simple`）；
   - SKU 重新随机生成，价格改为目标 USD 价；
   - 创建成功后把新商品回写本地 `site_products` / `site_product_variations`
     快照表（简单商品按"主商品自身作为唯一变体"落库），后续订单可直接匹配到它。
3. 创建过程的健壮性处理：
   - POST 请求连接异常时，会先按 SKU 查一次远端，确认"是不是其实创建成功了，
     只是响应丢包"，避免误判失败又重复创建。
   - SKU 冲突（`product_sku_already_exists`）时重新生成 SKU 重试，最多
     `CREATE_SKU_RETRIES`（3）次。

### 3. 同价商品复用（避免站点堆积重复商品）

按"目标 USD 单价"复用已创建的商品，优先级：

1. **本次运行内**已创建的同价商品（同一次下单里多行同价，只建一次）；
2. **补单重试**时上一轮（`reusableCreated`）已创建的同价商品（幂等，避免重试
   反复建号）；
3. 都没有才真正调用站点 API 新建。

### 4. 返回结构

与 `matchItems()` 基本一致，每行多两个字段：
- `source_variation_id`：来源变体 ID（同价命中或复制模板的变体）；
- `auto_created`：是否为本次自动新建的商品。

---

## 三、两种模式的关键差异

| | RANDOM 模式 | CREATE 模式 |
|---|---|---|
| 输入 | 一个目标金额 | 商户已传的逐条商品明细（各自带目标单价） |
| 商品数量/组合 | 系统随机凑单决定 | 与商户明细行数一一对应 |
| 找不到合适商品时 | 改价补齐已选商品（不新建） | 复制模板、在站点新建商品 |
| 是否调用远程站点 API | 否 | 是（同步调用，不走队列） |
| 典型场景 | 商户下单未传商品明细，系统自动配单 | 商户下单已传商品明细，需要站点上真实存在同价商品 |

## 四、可调参数（`SystemConfig`）

| Key | 默认值 | 含义 |
|---|---|---|
| `order_match.max_item_quantity` | 3（0 表示不限制） | RANDOM 模式单个变体件数**随机上限**的临界值 |
| `order_match.min_price_ratio` | 0.4 | RANDOM 模式末件改价的最低折扣比例（改价/原价） |

代码内常量（非配置）：

| 常量 | 值 | 含义 |
|---|---|---|
| `RANDOM_POOL_SIZE` | 10 | 每轮随机候选池大小 |
| `MAX_BACKTRACK_ROUNDS` | 3 | 末件补齐回溯退量的最大轮次 |
| `CREATE_PRICE_TOLERANCE` | 5% | CREATE 模式同价匹配的相对容差 |
| `CREATE_SKU_RETRIES` | 3 | 远端建品 SKU 冲突重试次数 |
| `CREATE_HTTP_TIMEOUT` | 60s | CREATE 模式调用站点 API 超时 |
